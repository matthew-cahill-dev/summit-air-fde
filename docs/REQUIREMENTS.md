# Requirements traceability

How each stated requirement is met, where the code is, which automated tests cover it, and which live call demonstrates it. "Prompt" means the model is instructed in `vapi/system-prompt.md`. "Backend" means a rule enforced in code that the model can't override.

Live scenario numbers refer to the **Suggested scenarios** in the [README](../README.md#for-revin-reviewers). Simulation ids refer to `vapi/simulations/*.json` (run with `npm run evals`; see [TESTING.md](TESTING.md)).

Every tool result's `say` ends with the next step (required by the `ToolOutcome` type). Every non-booking path ends in a record (priority dispatch, callback, safety follow-up). **Prompt:** read-back before booking, recap after, never claim an action without `ok: true` | `book-appointment.ts`; `repositories/scheduling.ts` (`claimSeat`); `priority-dispatch.ts`; `callback-request.ts` | `booking.test.ts` (concurrency, idempotency, slot_taken), `dispatch-callback.test.ts`, `tools-endpoint.test.ts`, `call-outcome.test.ts` | Scenarios 1–3; sims `a-new-customer-tuneup`, `f-reschedule` |

## Coverage gaps (honest)

- The automated suite tests the backend and the prompt *text*, not the model's behavior. Model behavior is covered by the live calls (log in [TESTING.md](TESTING.md)) and by the Vapi simulations, which are built but **not yet run** against the live assistant (each run spends Vapi credits).
- See [LIMITATIONS.md](LIMITATIONS.md) for what is deliberately not built.
